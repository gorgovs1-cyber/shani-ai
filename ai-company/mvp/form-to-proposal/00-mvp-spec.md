# 00-mvp-spec.md — Form-to-Proposal MVP (Sprint 1)

> תת-מסמך תפעולי תחת סמכות `00-company-constitution.md` → `01-company-architecture.md` →
> `02-capability-map.md`. אינו מתקן אף אחד מהם. מסמך MVP צר: הגדרה בלבד, אין קוד, אין agents.

## 1. מטרת ה-MVP

לבנות את המסלול הראשון והמצומצם ביותר שמוכיח ערך אמיתי: לקוח ממלא טופס אבחון → המידע
מנורמל ומאומת → הצורך העסקי מנותח → מומלצים פתרונות Shani AI מתאימים → מוכנים קלטי-תמחור →
נוצרת טיוטת-הצעה פנימית → שני בודקת, עורכת ומאשרת. **אין שליחה אוטומטית ללקוח בשום שלב.**

## 2. פונקציונליות קיימת לשימוש חוזר

| רכיב | מצב מאומת |
|---|---|
| `public/audit/index.html` | טופס HTML סטטי מלא (Heebo/RTL), עם JS שלם: `collect()`/`send()`/`done()`/`waFallback()`, ולידציית-אימייל בסיסית (regex) |
| Route `/audit` | Rewrite ב-`next.config.js`: `/audit → /audit.html` (root, **לא** ל-`audit/index.html`) |
| `public/audit.html` | **קובץ שונה, לא זהה** — חתוך/לא-שלם: מסתיים באמצע פונקציה, **חסרות** `collect/send/done/waFallback`. זה הקובץ שה-route החי בפועל מגיש |
| `app/pricing/page.tsx` | נתוני שירותים/חבילות/מחירים אמיתיים (עברית+אנגלית), כולל "AI Audit עצמאי ₪450" |
| `components/AnalyticsScripts.tsx` | `trackLead()` — פונקציית GA4/Meta מוכנה לשימוש חוזר |
| `.env.example` | תשתית env server-side קיימת (Supabase, cron) — כרגע לא משמשת את טופס-האבחון |
| Marketing Engine (`researcher/creator/reviewer.md`) | דפוס-תבנית מאומת ל"ניתוח→יצירה→ביקורת עצמאית" — ניתן ללמוד ממנו מבנית, **לא לגעת בו** |

## 3. פונקציונליות חסרה (מאומת, לא בריפו)

ניתוח-AI וכתיבת-הצעה **מתוארים בעמודי-שיווק** (`automations`, `ai-consulting`) כמתבצעים
דרך n8n חיצוני (`shanicreates.app.n8n.cloud`) + Claude — **אין קוד/פרומפט/סכימה של כך בריפו
הזה**. אין: route/server action לקליטת הטופס בתוך Next; אחסון תשובות-טופס; שלב נירמול/ולידציה
בקוד; ניתוח-צורך; מנוע-המלצת-פתרון; הכנת-קלט-תמחור; יצירת-טיוטת-הצעה; מסך-בדיקה/עריכה/אישור
לשני. **הנחה שדורשת אימות משני:** מה בפועל קורה היום ב-n8n (אינו נגיש מהריפו).

## 4. זרימת משתמש מדויקת

לקוח פותח `/audit` → ממלא טופס → שולח → קליטה+נירמול+ולידציה → ניתוח-צורך עסקי → המלצת
פתרון(ות) → הכנת קלטי-תמחור → יצירת טיוטת-הצעה פנימית (סטטוס `draft`) → שני רואה, עורכת,
מאשרת/דוחה → **עצירה. אין שליחה אוטומטית ללקוח בשום מצב.**

## 5. שדות טופס נדרשים

תיאור-עסק · מטרת 3-חודשים · תיאור יום-עבודה · משימה חוזרת מעייפת · מקור-לקוחות עיקרי ·
תהליך אחרי-פנייה · כלים בשימוש · מצב אתר/נוכחות דיגיטלית · מה הכי חסר · הבעיה הדחופה ביותר ·
רמת-דחיפות · שם מלא · אימייל (**MUST** תקין) · טלפון/וואטסאפ. שדות חובה מינימליים ל-MVP:
תיאור-עסק, הבעיה הדחופה, שם, אימייל.

## 6. פלט ניתוח פנימי

סיכום-צורך מנורמל · תחומי-כאב מדורגים · אותות-דחיפות · פערי-מידע (מה חסר/סותר להמשך).
סוג-מימוש: AI-assisted analysis (על קלט הטופס בלבד — לא תוכן חיצוני לא-מהימן, חוקה §17).

## 7. פלט פתרון מומלץ

1–3 הצעות פתרון תואמות ל-Shani AI (למשל: אתר, אוטומציית n8n, סוכן-AI), עם נימוק קצר לכל
המלצה. סוג-מימוש: AI-assisted analysis, בכפוף לרשימת-שירותים מאושרת בלבד (סעיף 2).

## 8. פלט קלטי-תמחור

טווח-מחיר ראשוני מבוסס `app/pricing/page.tsx` (לא סכום סופי-מאושר) · היקף-עבודה משוער ·
הערות-מורכבות. סוג-מימוש: deterministic application logic (מיפוי מול טבלת-מחירים קיימת).
**אינו** Approved Commercial Terms (FIN-04, שער נפרד, כספים בלבד).

## 9. פלט טיוטת-הצעה

מסמך-טיוטה יחיד: תמצית-צורך, פתרון(ות) מומלץ, טווח-מחיר, צעד-הבא מוצע. סטטוס תמידי:
`draft` עד אישור שני. סוג-מימוש: AI-assisted analysis + deterministic template.

## 10. גבול אישור אנושי

**[אילוץ חוקתי, ארכיטקטורה §5.1/§8]** שני היא המאשרת היחידה של Proposal לפני כל שליחה
ללקוח. המערכת מפיקה טיוטה — לעולם לא התחייבות מסחרית מחייבת. עריכה/דחייה/אישור — שני בלבד.
סוג-מימוש: human decision.

## 11. נתונים שחייבים להישמר

תשובות-טופס גולמיות · גרסת-נירמול · תוצר-ניתוח · המלצות-פתרון · קלטי-תמחור · טיוטת-הצעה +
היסטוריית-עריכה + סטטוס-אישור. בעלות: מכירות (Lead/Business Need/Proposal), עיצוב-פתרון
(המלצת-פתרון כ-Solution Assessment), כספים (קלט-תמחור בלבד — לא Approved Commercial Terms).

## 12. טיפול בשגיאות ועצירה בטוחה

**[אילוץ חוקתי, חוקה §15]** מידע חסר/סותר בטופס → בקשת-הבהרה, לא ניחוש. כשל בשלב-ניתוח →
עצירה + דיווח, לא המשך עם פלט-חלקי מוסתר. אין קטגוריית-פתרון מתאימה → מצב-סיום "לא מתאים",
לא הצעה מאולצת. סוג-מימוש: deterministic logic + human decision (הסלמה לשני בספק).

## 13. מפורשות מחוץ-לתחום (MVP זה)

שליחת-הצעה אוטומטית · אישור-מחיר אוטונומי · חוזים · חשבונאות · גביית-תשלום · CRM מלא ·
אוטומציית-תמיכה · אוטומציית-הפקה · אוטומציית-שיווק · Control Plane כלל-חברתי · agents
מרובים חדשים · ידע-משתנה-עצמית · מחקר-אינטרנט לא-מוגבל · תיקון `public/audit.html` השבור
(פער נפרד, לא בתחום Sprint 1 — טעון החלטת שני).

## 14. קריטריוני קבלה

טופס תקין נקלט ומנורמל; קלט חסר/פגום נעצר ומבקש הבהרה, לא מנחש; מופק ניתוח-צורך אחד לכל
הגשה; מומלץ 1–3 פתרונות עם נימוק; מופק טווח-תמחור לא-סופי; מופקת טיוטת-הצעה יחידה בסטטוס
`draft`; שום דבר לא נשלח ללקוח בלי אישור שני מפורש ומתועד; כל שלב ניתן לייחוס (מי/מה/מתי).

## 15. רצף מימוש קטן לגרסה הראשונה

1. תיקון/איחוד `public/audit.html` מול `audit/index.html` — **deferred**, טעון החלטת שני.
2. קליטת-טופס + נירמול + ולידציה — deterministic application logic.
3. שלב ניתוח-צורך על קלט מנורמל בלבד — AI-assisted analysis.
4. מיפוי-פתרון מול רשימת-שירותים קיימת — AI-assisted analysis + deterministic mapping.
5. קלט-תמחור מול `pricing/page.tsx` — deterministic application logic.
6. הרכבת טיוטת-הצעה + שמירה בסטטוס `draft` — deterministic template + AI-assisted analysis.
7. מסך/ערוץ בדיקה-עריכה-אישור לשני — human decision, ללא מעקף.
